# Управление исходным кодом

Используется GitHub Flow: короткоживущая ветка от main, коммиты, pull request, проверки, слияние.
Настройка инструментов выполняется в ci/quality-check, перенос прототипа — в отдельной ветке.

## Коммиты

Формат: `type(scope): описание`, scope необязателен, заголовок до 100 символов.
Типы: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert.
Один коммит соответствует одной задаче. Для несовместимых изменений допускается `!`.

После клонирования выполните `git config core.hooksPath .githooks`.
Хук проверяет сообщение локально, CI повторяет проверку для новых коммитов.
Начальный коммит проверяется при первой публикации ветки с CI.

## Pull request

После успешного первого запуска Quality в Settings → Branches настройте защиту main:
обязательный PR, успешные commits/backend/frontend/metrics/build, актуальность ветки,
запрет обхода правил. Force push и удаление main запрещены.
Обязательное чужое одобрение для индивидуального проекта не включается.

В Settings → General → Pull Requests разрешите Squash and merge.
Итоговый заголовок должен соответствовать Conventional Commits, например
`ci: configure quality checks and metrics`. CI проверяет коммиты ветки;
изменённое вручную сообщение squash нужно проверить перед подтверждением слияния.
После слияния push в main дополнительно проверяет новый коммит.

Один PR создаёт один коммит в main. CI проверяет состояние при каждом push и обновлении PR,
а не каждый промежуточный коммит пакетной отправки отдельно.

## Релиз

После успешной проверки main создаётся аннотированный тег версии, например v0.1.0,
и GitHub Release. К релизу прикладывается prototype-build из запуска для SHA тега.
Существующие теги не перезаписываются. Развёртывание не автоматизировано.
