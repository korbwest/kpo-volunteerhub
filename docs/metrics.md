# Метрики качества

Все пять групп собираются автоматически в Quality и публикуются в quality-metrics/metrics.json.

| Группа | Источник | Единица |
| --- | --- | --- |
| Ошибки и предупреждения линтера | Ruff JSON, ESLint JSON | число нарушений |
| Покрытие строк | pytest-cov, Vitest coverage | процент |
| Пройденные и упавшие тесты | JUnit XML | число тестов, пропуски отдельно |
| Время тестов | JUnit XML | секунды |
| Частота коммитов | git log, полная история | коммиты за 7 суток и среднее за сутки |

Backend и frontend показываются отдельно. Проценты покрытия не усредняются.
Нарушения Ruff считаются ошибками; ESLint разделяет ошибки и предупреждения.
Форматтеры проверяются отдельно. Время JUnit не равно длительности workflow.
Служебные тесты скриптов не включаются в число тестов приложения.
Отсутствующий отчёт — null и ошибка полноты, а не ноль нарушений.
Поле complete подтверждает наличие данных, но не успешность тестов: её определяют задания CI.

Частота учитывает достижимые из измеренного SHA коммиты без merge-коммитов.
Используется время фиксации (committer timestamp), окно (конец − 7 суток, конец], UTC.
Конец окна — момент вычисления. Сохраняются границы, SHA и список учтённых коммитов.
Среднее равно N / 7, включая дни без коммитов. Нужна полная история fetch-depth: 0.
В PR проверяется тестовое объединение с main; служебный merge-коммит исключён.
В main после squash считаются принятые изменения, а не все коммиты рабочей ветки.
Это показатель фиксации изменений, не оценка трудозатрат.

Замеры выполняются на завершении lab5, lab6, lab7 и final согласно графику работ.
В Actions → Quality → Run workflow выбираются main и stage. Сохраняются JSON/XML,
ссылка запуска, SHA и дата; Insights можно использовать дополнительно.
Артефакты нужно скачать до истечения срока их хранения на GitHub.

Первый замер CI относился к технической основе: /health и стартовой странице.
После переноса прототипа измеряется расширенный набор тестов API и интерфейса;
результаты первого замера нельзя использовать как покрытие нового кода.
При наличии backend/alembic.ini CI проверяет применение миграций и соответствие схемы PostgreSQL.
